# 0.6.0 — AUTOSTART & SELF-HEAL — Entwicklervertrag

## Ziel

`0.6.0-autostart-selfheal` soll einen normalen Linux-Nutzer vom Projektordner bis zum lokal erreichbaren Dashboard führen, ohne dass Portkonflikte, stale Marker, beschädigte lokale JSON-Zustände, eine beschädigte Runtime-Datei oder eine schreibgeschützte Quelle sofort manuelle Reparatur erzwingen.

Status während dieses Slices: `development / draft`. Die bewiesene Runtime-Baseline 0.5.1 bleibt unverändert; Native L4 bleibt **OFFEN**.

## Start-State-Machine

1. Runtime-Basis lokalisieren.
2. Tatsächliche Schreibbarkeit prüfen.
3. Bei Read-only Quelle in benutzereigenen Bereich spiegeln.
4. grafische Startansicht öffnen oder im Headless-Testmodus bewusst überspringen.
5. stale PID bereinigen.
6. Release-Recovery für immutable Assets ausführen.
7. lokale Kernzustände validieren/reparieren.
8. Runtime-Preflight ausführen.
9. gewünschte Portbasis normalisieren und eine passende/freie Loopback-Instanz bestimmen.
10. Backend starten oder passende vorhandene Instanz wiederverwenden.
11. READY-Status mit korrekter Version prüfen.
12. Browser auf Dashboard umleiten und Browser-/Dashboard-Handshake bestätigen.
13. Launcher-Report schreiben.

## Reparaturprinzipien

- **fail closed:** unbekannter oder widersprüchlicher Zustand wird nicht als gesund angenommen.
- **preserve before replace:** beschädigte Nutzerdaten und Runtime-Dateien werden vor Ersatz quarantänisiert.
- **backup before default:** ein validierbares Backup hat Vorrang vor einem Reset auf Standardwerte.
- **source is sacred:** Runtime-Recovery ist in Source-Checkouts deaktiviert.
- **no system surgery:** keine Systempakete, kein sudo, keine globalen Konfigurationsänderungen.
- **bounded automation:** Portscan, Wartezeiten und Browserversuche sind begrenzt.

## RECOVERY_BASIS

`scripts/build_recovery_basis.py` erzeugt aus exakt `manifests/RUNTIME_MANIFEST.json`:

```text
RECOVERY_BASIS.zip
├── RECOVERY_MANIFEST.json
└── files/
    └── <jede Runtime-Allowlist-Datei>
```

`RECOVERY_MANIFEST.json` enthält pro Datei Pfad, Größe und SHA256. Der Builder verwendet feste ZIP-Zeitstempel und sortierbare, deterministische Metadaten. `--check` verifiziert Dateimenge und Einzelhashes nach dem Build erneut.

## Failure-Matrix

Die erste verbindliche Matrix enthält:

| ID | künstlicher Fehler | erwartete Reaktion |
|---|---|---|
| FM-001 | ungültiger Portwert | verständlicher Fallback auf 8765 |
| FM-002 | gewünschter Port belegt | freier Loopback-Port wird gewählt |
| FM-003 | stale PID | Marker wird entfernt |
| FM-004 | Haupt-JSON kaputt, Backup gültig | Original quarantänisiert, Backup restauriert |
| FM-005 | Haupt- und Backup-JSON kaputt | beide quarantänisiert, validierter Standard |
| FM-006 | Source-Checkout ohne Release-Marker | Recovery deaktiviert, keine Mutation |
| FM-007 | Release-Asset hashabweichend | altes Asset quarantänisiert, Recovery-Kopie restauriert |

Die Matrix schreibt eine maschinenlesbare JSON-Evidenz und liefert Exitcode 1, sobald ein Fall scheitert.

## Portable-Build

`scripts/build_portable.py` verwendet den in `requirements-build.txt` exakt gepinnten PyInstaller. Das Ergebnis ist ein Linux-x86_64-onedir-Paket mit:

- `AIO-Tool-Start` — gebündelter Python-Launcher,
- `_internal/` — Python-Runtime und Runtime-Allowlist,
- `_internal/MANIFEST_RELEASE.json`,
- `_internal/RECOVERY_BASIS.zip`,
- `start_tool.sh`,
- `start_tool.desktop`,
- `PORTABLE-INFO.txt`.

Das finale Portable-Paket wird als ZIP plus SHA256 ausgeliefert.

## Portable-Smoke

`scripts/portable_smoke.py` prüft zwei reale Ausführungsfälle des gebauten Pakets:

1. **normal-writable:** `AIO-Tool-Start --no-browser --preflight-only` muss erfolgreich abschließen.
2. **read-only-source-mirror:** Paketbaum wird schreibgeschützt; der Launcher muss selbstständig einen benutzereigenen Spiegel erzeugen und den Preflight dort erfolgreich abschließen.

Damit wird nicht nur der Builder, sondern das tatsächlich gebaute Artefakt ausgeführt.

```text
  → 08-firefox
```

### 01 Core-CI

- Python compileall
- vollständige Unit-/Integrationtests
- Foundation Validation
- Manifest Guard
- Learning Guard
- Evidence Guard
- Documentation Guard
- Shell-/JavaScript-Syntax
- Runtime-Release-Build + Check

### 02 Failure-Matrix

Deterministische künstliche Fehlerfälle, JSON-Evidenz.

### 03 Source-ZIP

`git archive HEAD`; dadurch ist das Source-Artefakt unmittelbar an den geprüften Commit gebunden.

### 04 RECOVERY_BASIS

Build + vollständige Nachprüfung + SHA256.

### 05 Portable-Build

Gepinnter PyInstaller + Strukturprüfung + ZIP + SHA256.

### 06 Portable-Smoke

Normaler und Read-only-Ausführungsfall auf dem tatsächlichen Portable-Artefakt.

### 07 Chromium / 08 Firefox

Strikte bestehende Render-, Reflow- und Interaktions-Acceptance auf getrennten Browsergates.

## Promotion-Regel

`development / draft` bleibt bestehen, solange nicht alle acht Gates für **denselben Commit** erfolgreich beendet sind. Erst danach dürfen Commit, Run-ID, Artefakthashes und Browsermatrix in einen separaten Evidenz-/Promotion-Schritt übernommen werden. Native L4 bleibt unabhängig davon **OFFEN**.
